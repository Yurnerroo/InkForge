feat(launcher): required FONTS folder, blocking structure validation, export_results PDF naming

- Content Checker's scanner now excludes a FONTS (case-insensitive)
  subfolder from page scanning, so it never shows up as a fake page in
  manifest.json (real bug seen with a Document fonts folder).
- New content_checker.structure_validator.validate_issue_structure():
  fast, blocking checks (folder exists, FONTS subfolder present, at
  least one page folder, no empty page folder unless profile marks it
  manual) plus soft warnings (empty FONTS folder, unrecognized
  subfolders). Wired into a new POST /api/validate_structure endpoint
  and as a precondition of /api/check.
- FONTS is no longer a separate ExecuteRequest argument / GUI field --
  /api/execute now always looks for {issue_folder}/FONTS itself and
  blocks with a clear message if missing, then always provisions fonts
  before running the layout script. Removed /api/pick_fonts_folder.
- New launcher.pdf_naming module computes
  export_results/{TYPE}_{week}({total})_{n}.pdf automatically when
  pdf_path is omitted from /api/export_pdf (still overridable manually).
- Updated the launcher UI: removed the FONTS browse field, added a
  structure-validation status area wired to /api/validate_structure
  that blocks step 1 until the issue folder passes, added a total
  publish count field, made the PDF path field optional.
- Updated docs/content-structure.md, docs/architecture.md and
  docs/first-run-checklist.md accordingly.
- Updated/added tests (146 passing): scanner FONTS exclusion,
  structure_validator, pdf_naming, and launcher app tests for the new
  blocking behavior and PDF auto-naming.
